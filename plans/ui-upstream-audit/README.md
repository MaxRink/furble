# UI audit: upstream gkoh/furble, fork master, PR #273

Three-way visual comparison of every reachable UI page, on every modeled board,
in both navigation layouts, at every text size, in every legend placement.

| tree | commit | what it is |
| --- | --- | --- |
| upstream | `2b79ce8d` | gkoh/furble master, "Add support for M5StickC Plus SE (#286)" |
| master | `6245a301` | MaxRink/furble master, the base of PR #273 |
| #273 | `a978add5` | `fix/notouch-layout-overflows` head |

`git merge-base upstream/master 6245a301` is `2b79ce8d` itself, so fork master
is upstream master plus 715 commits with no divergence. Every difference below
is something the fork did, not something upstream changed afterwards.

## How upstream was rendered

Upstream has no simulator. Overlaying the fork's `sim/` onto the upstream tree
does not build: upstream is missing ten `src/*.cpp`, seven `lib/furble/*.cpp`
and eight headers the simulator compiles.

The inverse overlay does build, and it is what produced the upstream captures.
The fork tree at `6245a301` is kept whole and only upstream's UI is swapped in:
`src/FurbleUI.cpp`, `include/FurbleUI.h`, `src/FurbleUIIntervalometer.cpp`,
`src/FurbleSpinValue.cpp`, `include/FurbleSpinValue.h` and `include/interval.h`.
That needed:

- eight mechanical API fixes, all of them the fork's own later changes to code
  upstream calls: `CameraList::get/last` now return `shared_ptr<Camera>`, and
  the GPS parser accessor became `getStatusSnapshot()`
- seven one-line battery and intervalometer stubs, because the fork's
  `FurbleCompanionService.cpp` calls UI accessors upstream does not have
- about 200 lines of grafted `FURBLE_SIM` seams: the request plumbing,
  `simScenarioAction`, `simQueryState`, `simulatorHome`, `simulatorBack`, a
  `simPressButton` stub, and the driver tick and exit check in `UI::task`
- `src/FurbleUIBulb.cpp` dropped from `sim/build.sh`, since upstream has no
  bulb mode

**This is upstream's real layout code, not a fallback commit.** Nothing about
the geometry, the fonts, the row counts or the indicator placement came from
the fork. The overlay is uncommitted and lives only in the audit worktree.

Upstream renders 15 of the 26 audited pages. The other eleven (`text_size`,
`sensors`, `infrared`, `gps_rate`, `bluetooth`, `power`, `feedback`,
`storage`, `bulb`, `bulb_duration`, `cameras`, `level`) do not exist
upstream. They are new features, so they cannot be regressions, and they are
listed separately below.

## The reference text size

Upstream has no text size setting. Its three captured sizes are byte-identical,
verified across all 90 upstream images, and they match the fork's **normal**
size. Every upstream-versus-fork claim in this document is therefore made at
normal. The small and large tables are still included, but in those the
upstream column is the same image repeated and only the master versus #273
column carries information.

The fork's own size range is board-clamped: 320x240 renders small and normal
identically, 80x160 renders normal and large identically.

## How a regression was decided

Pixel differences alone do not separate a regression from a new feature, so the
verdict is the simulator's own `ui.overflow` query, which reports whether the
current page has scrollable content above or below the viewport. A page that
fits upstream and scrolls on the fork is a regression: content that was on
screen now needs the encoder to reach.

The same query was added to the upstream graft, using the identical
`lv_obj_get_scroll_top` / `lv_obj_get_scroll_bottom` implementation the fork
uses, so the three readings are produced by the same code.

### About

Upstream shows two rows, Version and ID. `e2bdd589` added Build, IDF and Reset.
Five rows do not fit any of the three panels, so the page scrolls everywhere.
This is the clearest regression in the set: it affects every board, both
layouts, every text size, and #273 does not touch it.

### GPS settings

Upstream has one setting row plus the GPS Data entry. The fork added Rate,
Sentences and Constellation (`f96980d1`) and then Assist (`5b343bfa`). The page
scrolls on 135x240 and 320x240. On 80x160 it already scrolled upstream, so that
panel is not a regression.

### Connected page on the Core

Upstream puts three entries on this page. The fork put eight into the same
three-column, two-row grid. Plan 168 already documents the consequence: three
entries share cell (1,1) and draw through each other. #273 reworks the grid and
closes the buttons-layout collision, but see the next section for what it does
to the touch layout.

### Regressions PR #273 introduces

`display` fits on master on every panel and both layouts, and scrolls on #273
in all eighteen combinations. The cause is in the branch's own commit message:
`addDisplayMenu` changed from `lv_obj_set_height(cont, LV_PCT(100))` to
`LV_SIZE_CONTENT` with a `min_height` floor, because pinning the container to
the page height left `LV_FLEX_ALIGN_SPACE_EVENLY` no free space to distribute
and it packed rows on top of each other, ten overlapping pairs at normal on
135x240. So this is a deliberate trade of overlap for scrolling, not an
oversight, and it is recorded here because the audit measures the scroll, not
the overlap. It is still worth a second look: the page now scrolls on the
320x240 Core, which has room to spare and had neither problem.

`tx_power` on 80x160 buttons and `connected` on 320x240 touch at small and
normal are the same shape of finding and are not explained in the plan.
`connected` on 320x240 touch is the one plan 168 claims to fix; at maximum text
size it does fix master's 23 px overflow, but at small and normal it introduces
an overflow master did not have.

## The Remote shutter page is not regressed

At the reference text size the Remote page is upstream's, unchanged, on every
panel:

| panel | layout | upstream vs master |
| --- | --- | --- |
| 135x240 | buttons | 18 px, the battery icon in the header |
| 135x240 | touch | 18 px, the battery icon in the header |
| 80x160 | buttons | 144 px, all of it in the header band, y 0 to 20 |
| 80x160 | touch | 144 px, header only |
| 320x240 | buttons | 18 px, battery icon |
| 320x240 | touch | 18 px, battery icon |

The page body is pixel-identical. The lock icon, the grey leader line, the
indicator icons and the overflow all match upstream exactly. #273 changes it in
the buttons layout only, by removing the leader line, and leaves the touch
layout byte-identical to master.

There is nothing to bisect here, so no bisect was run. A capture bisect over
the 715 commits would in any case be unsound: the scenario DSL, the seed names
and the query namespace all postdate most of that range, so a modern scenario
cannot run against an old binary. Where attribution was needed it came from
`git log -S` on the strings each commit introduced, which is exact.

## Simulator fidelity gap found while doing this

`action page shutter` renders the wrong page state. The fork's `PAGE` handler
only calls `lv_menu_set_page`; it never calls
`configureControl(ControlMode::SHUTTER)`. The Remote page therefore draws with
the menu-mode legend, up arrow, tick, down arrow, instead of the shutter-mode
legend, back arrow, camera, focus, which is what the device shows and what
`configShutterControl` sets.

The first pass of this audit captured the page that way and read it as a fork
regression. It was not; it was the verb. `action blind` does call
`configureControl`, and `sim/scripts/docs-gallery.txt` already uses it. Every
capture in this document uses `blind`.

Recommendation: make `page shutter` configure the control the way the device
does when that page loads, so the two verbs cannot disagree. Failing that,
document `blind` as the only valid way to reach the Remote page and say plainly
in `docs/sim.md` that `page shutter` renders a state the firmware never enters.
Any existing scenario that asserts Remote page geometry after `page shutter` is
measuring the wrong legend.

## Pages that exist only on the fork

No upstream counterpart, so no regression is possible. Recorded because several
of them scroll at the fork's own default text size:

- scroll on all three panels: `bluetooth`, `power`, `storage`, `bulb_duration`
- scroll on 135x240 and 80x160 and 320x240 buttons: `infrared`
- scroll on 80x160 only: `sensors`, `feedback`, `bulb`, `cameras`

`level` needs `seed imu true`; the entry is hidden without it, which is why
`action nav level` returns UNAVAILABLE in a plain run. It is captured here
through a separate one-step scenario and does not overflow on any board.

## Method

- Each tree built for all three panels with `sim/build.sh`, `FURBLE_SIM_RIG=0`.
- One scenario per tree walks every page and writes a PNG, driven by the
  deterministic `action nav` and `action page` verbs plus `action blind` for
  the Remote page. `FURBLE_SIM_IR`, `FURBLE_SIM_FEEDBACK` and `FURBLE_SIM_SD`
  are on so the optional submenus exist.
- Text size through `FURBLE_SIM_TEXTSIZE`, legend placement through
  `seed legend 0|1`. Legend is a #273-only setting, so master and upstream have
  one placement and #273 has two. `lg0` is the Buttons placement master ships.
- Captures are byte-deterministic: a repeat run of all 26 pages on one binary
  produced 26 identical files.
- Diffs by a stdlib PNG decoder, reporting changed pixel count and bounding box.
- 1485 captures, quantised to a palette and recompressed, 6 MB.

Layout directories are `buttons` and `touch` for upstream and master, and
`buttons-lg0`, `buttons-lg1` and `touch` for #273. `buttons-lg1` has no
counterpart in the other two trees because the setting did not exist.

## The second legend placement

`buttons-lg1` is the Bottom legend placement PR #273 adds. It has no
counterpart in upstream or master, so it appears in no comparison table. The
captures are under `captures/273/<panel>/buttons-lg1/<size>/`, 234 images
covering the same 26 pages on all three panels at all three text sizes.
