# PR60: Nikon Z50II smart device support (upstream issue 257)

## Motivation

Upstream issue 257: "Currently a hardcoded `Z50II_SMART_DEVICE_KEY` is used to
make the smart-device handshake work ... Because of that, this setup currently
works only when a valid SnapBridge pairing already exists on the camera."

The reporter wants GPS sync from a sidecar instead of SnapBridge. That is the
same reason plan 14 and plan 15 exist here. Nikon smart mode is the only Nikon
path that carries geotagging, so it matters to this fork.

This document is analysis only. It does not propose a Nikon feature PR. The one
code change that ships with it is a small diagnostic fix in the smart device
failure path.

## Scope

- Read of the Nikon code paths on fork master.
- Root cause ranking for issue 257 and the Z6III follow up in the same thread.
- What the reporter's patch does and which parts are safe to adopt.
- One small change: report the smart device limitation without a 10 second
  stall.
- Out of scope: any Bluetooth Classic work, any Bluedroid migration, any
  captured key import.

## The symptom, restated

Two reporters, two bodies:

1. h3ifri, Z50II, XIAO ESP32S3. A Codex written patch gets BLE connect, the four
   stage handshake, AF, shutter, time sync and GPS all working. It only works
   because the camera already holds a SnapBridge pairing and because the 8 byte
   smart device identifier was lifted from an HCI snoop log.
2. herrfrei, Z6III, applied that patch. Connect and commands worked. Every GPS
   write failed with `rc: 384`, which is ATT error 0x80.

gkoh's position in the thread: the handshake is cryptographic and either
succeeds or fails, and the key must be obtainable without SnapBridge. He then
built a Bluedroid proof of concept and concluded that Bluedroid cannot host
Fujifilm, Sony and Nikon smart in one build because of its LE privacy handling.

## Analysis

### H1: first time smart pairing needs Bluetooth Classic. Confidence: high

The Nikon smart device pairing does the four stage Blowfish exchange over BLE
and then swaps to Bluetooth Classic to complete a secure simple pairing bond
with numeric comparison. Only after that does the camera store the smart device
identifier that the BLE handshake later presents.

Evidence in the thread. The reporter's own Bluedroid proof of concept on an
ESP32 DevKit shows the transition directly:

```
status=5 msg=BLE done
status=6 msg=BT inquiry
[CLASSIC] SPP pre-auth connect
[CLASSIC] IO capability request
[CLASSIC] Numeric value: 004689
[CLASSIC] Authentication complete
status=8 msg=Pairing complete
```

That run also needed a Bluedroid source patch in `btm_sec.c` to send
`auth_req = BTM_AUTH_AP_YES` in the IO capability reply, otherwise the bond did
not survive a camera reboot and the camera switched Bluetooth off.

Evidence in this tree. `lib/furble/NikonSmart.cpp:177-182` already says so:

```
// Unable to continue at this time
// For some reason Nikon smart device pairing swaps to Bluetooth Classic to
// establish secure bond and our Bluetooth stack is LE only.
```

Consequence for this fork. furble is NimBLE, which is LE only. The reference
board M5StickC Plus 2 is a classic ESP32 and has a Classic radio, so a Bluedroid
port could in principle pair there. The M5StickS3 used for hardware tests here
is an ESP32-S3 and has no Classic radio at all, so it can never complete a first
time Nikon smart pairing regardless of stack. Same for C3 and C6.

This is the blocker. It is not fixable in this fork. The external findings below
confirm it independently: no project anywhere completes a first time Nikon smart
pairing without a Bluetooth Classic bond, and the Bluetooth mechanism that might
have helped, cross transport key derivation, is defined only for devices that
have both radios.

### H2: the smart path is deliberately dead code. Confidence: certain

Even with a camera that already holds a valid identifier, fork master cannot use
smart mode:

- `lib/furble/NikonSmart.cpp:182` returns `false` unconditionally at the end of
  `connectFinalise()`.
- `lib/furble/NikonSmart.cpp:185-199`: `shutterPress`, `shutterRelease`,
  `focusPress` and `focusRelease` are empty. There is no command
  characteristic discovery and no remote enable write.
- `lib/furble/NikonSmart.cpp:201` `updateGeoData()` is implemented, so
  geotagging is the only smart operation that exists today. It is unreachable
  because `connect()` never returns true.

So the correct reading of issue 257 is not "furble has a bug". It is "furble has
a stub, and the stub cannot be completed without Classic".

### H3: the 10 second final OK wait is wrong for Z series. Confidence: high

`lib/furble/NikonSmart.cpp:158-165`:

```cpp
bool NikonSmart::connectFinalise(void) {
  bool success = false;
  // wait for final OK
  BaseType_t timeout = xQueueReceive(m_Queue, &success, pdMS_TO_TICKS(10000));
```

This blocks for 10 seconds waiting for a `SUCCESS` notification on NOT1
(`0x2008`) after stage 4. Neither reporter log shows such a notification. The
reporter replaced the wait with a 200 ms poll and logged "No post-auth final OK;
continuing", and both the Z50II and the Z6III runs then proceeded.

Two consequences on fork master:

1. Every Nikon smart connect attempt stalls 10 seconds and then fails with
   "Timeout waiting for final OK." at `lib/furble/NikonSmart.cpp:164`.
2. Because the early return at `lib/furble/NikonSmart.cpp:167-169` fires first,
   the explanatory Bluetooth Classic message at
   `lib/furble/NikonSmart.cpp:180` is never reached. The user is told the wrong
   thing.

This stall is not covered by the connect timeout. `Control::connectAll()` passes
`TIMEOUT_INFINITE_MS` (`include/FurbleControl.h:74`, 5 s) to
`Camera::connect()`, but that governs link establishment only. The handshake
runs after the link is up. With infinite reconnect and the fork's backoff from
plan 09, a Nikon smart camera therefore burns 10 s of radio on every retry
before the backoff delay even starts.

This is the one part that is worth fixing now.

### H4: remote first characteristic selection may hide smart mode. Confidence: medium

`lib/furble/Nikon.cpp:111-121` picks the protocol by probing the pair
characteristic:

```cpp
auto *pairChr = pSvc->getCharacteristic(NikonRemote::REMOTE_PAIR_CHR_UUID);
if (pairChr == nullptr) {
  pairChr = pSvc->getCharacteristic(NikonSmart::PAIR_CHR_UUID);
```

`REMOTE_PAIR_CHR_UUID` is `0x2087` (`lib/furble/NikonRemote.cpp:11`),
`PAIR_CHR_UUID` is `0x2000` (`lib/furble/NikonSmart.cpp:28`). Remote wins when
both exist.

The reporter's patch reverses this and comments that "Z50II advertises the
remote channel too, but the working auth path starts on the smart-device pairing
characteristic". Their own log supports a body that exposes far more than the
smart set: NimBLE discovers `start_handle=64 end_handle=113` while the smart
characteristics they use sit at handles 66 to 99.

Do not adopt the reversal. Remote mode gives working shutter control today on
ML-L7 compatible bodies. Smart mode gives nothing. Flipping the preference would
turn a working remote shutter into a dead smart path on every body that exposes
both. If the preference ever becomes configurable it must default to remote.

Confidence is medium because the claim that a Z50II exposes `0x2087` comes from
a patch comment, not from a characteristic dump. A cheap way to settle it is one
console command that dumps the discovered characteristic UUIDs of the Nikon
service, which plan 27 already gives us the surface for.

### H5: the Z6III GPS failure is already fixed on fork master. Confidence: high

herrfrei's Z6III log in the thread:

```
sending GPS = 7f004e32280606450a3a33070b00c401ea07061010392f0001...
E NimBLERemoteValueAttribute: << writeValue failed, rc: 384 Unknown
```

`rc: 384` is `0x180`, the NimBLE encoding of ATT error `0x80`, an application
error from the camera. herrfrei then found and upstream merged the fix as
gkoh/furble PR 269, and it is in this tree after the Nikon refactor in
gkoh/furble PR 277:

- `lib/furble/NikonSmart.h`: `nikon_geo_t` carries separate `satellites` and
  `altitude_ref` bytes instead of one merged `extras` word.
- `lib/furble/NikonSmart.cpp:224`: `altitude_ref` is set to `'P'` or `'M'`.
  Leaving it `0x00` is what the camera rejected.
- `lib/furble/NikonSmart.cpp:253-279`: `degreesToDMSubMin()` uses the
  hundredths of a minute scaling `(*60, *100, *100)` rather than arc second
  scaling.

So the reported GPS failure would not reproduce against fork master. The payload
is correct now. It is still unreachable, for the reasons in H2 and H3.

Note also the second GPS constraint herrfrei reported: "GPS update only works,
when camera time and the time encoded in the GPS message is nearly in sync." The
external protocol document below says the camera does not adopt the timestamp in
the geo payload, so the camera is validating it rather than learning from it.
Any future smart PR needs an accurate clock on the sidecar, which GPS time
already gives us. Writing the separate time characteristic `0x2006`, declared
and unused in `lib/furble/NikonSmart.h`, is optional.

### H6: the reporter's other workarounds are ESP32-S3 or NimBLE artefacts, not Nikon

Their patch also disables `setSelfDelete`, drops the custom connect timeout and
connection parameters, removes RPA and the security setup from `Device::init()`,
and treats `connect() == false` with `isConnected() == true` as success. Fork
master already dropped `setSecurityAuth` and `setSecurityIOCap`, but still sets
`BLE_OWN_ADDR_RPA_PUBLIC_DEFAULT` at `lib/furble/Device.cpp:48`.

None of these belong in a Nikon change. The false negative connect they worked
around is an esp-nimble-cpp behavior on their board, and the RPA removal would
break Fujifilm secure. Reject all of it.

## What the reporter's identifier actually is

Worth stating plainly because the thread is ambiguous about it.

The four stage handshake needs no per camera secret. `SmartPairing` uses a fixed
Blowfish key (`lib/furble/NikonSmart.cpp:13-14`) and a fixed table of eight
salts (`lib/furble/NikonSmart.cpp:15-27`). Stage 2 verification just searches
the salt table for the entry where `hash(salt, camera_ts, our_ts)` matches the
identifier the camera sent (`lib/furble/NikonSmart.cpp:68-82`). Stage 3 derives
our reply the same way.

The hardcoded `Z50II_SMART_DEVICE_KEY` in the patch is not a crypto key. It is
`m_ID`, the 8 byte device identifier that furble normally generates randomly at
`lib/furble/Nikon.cpp:33-37` and persists in `nikon_t`. The camera accepts the
handshake only from an identifier already in its paired device list. That list
entry is created during the Classic bond. So the identifier is a consequence of
H1, not an independent secret to be derived.

That also means a captured identifier is enough to reconnect, which is exactly
what the reporter observed. It is not enough to pair.

## External findings

The prior art here is small. Three codebases and one writeup, all of them
downstream of furble's own reverse engineering. Every link below was fetched and
checked.

### Nobody does first time Nikon smart pairing over BLE only

This is the headline. It confirms H1 from outside the issue thread.

- <https://github.com/hurui200320/nsg> is the only independent reimplementation
  of the protocol. It is an Android app plus a Kotlin proof of concept plus an
  ESP32 firmware, and it explicitly targets the Z50II. Its README states: "The
  ESP32-S3 only supports BLE and does not have Bluetooth Classic, which the
  Nikon smart-device protocol requires for bonding" and "The original ESP32 has
  both BLE and Bluetooth Classic, which is why it is the target platform."
- <https://raw.githubusercontent.com/hurui200320/nsg/master/doc/nikon-z-gps.md>
  documents the sequence in full: after the BLE handshake and the ID write,
  close the GATT connection, run Classic discovery, `createBond()` on the
  Classic address, confirm the numeric passkey, wait for `BOND_BONDED`, then
  reconnect over BLE, and only then "GEO writes are permitted". It also notes
  "The camera exposes a different classic Bluetooth address than its BLE
  address."
- <https://raw.githubusercontent.com/hurui200320/nsg/master/esp32/README.md>:
  "Scans for a new Nikon camera, runs the 4-stage BLE handshake, bonds over
  Bluetooth Classic, and saves the camera info." So the nsg ESP32 firmware is a
  working reference for option B below.

Searches for a Python, bleak, Home Assistant or gphoto2 equivalent found
nothing. `octalide/niky` looks relevant but is not: it is a Nordic UART Service
bridge feeding NMEA to the camera's 10 pin port at 4800 baud.

### Cross transport key derivation does not rescue a BLE only part

The Bluetooth mechanism that would in principle let one bond cover both
transports is Cross Transport Key Derivation, CTKD, from Core Spec 4.2 onward.

- <https://www.kb.cert.org/vuls/id/589825>: CTKD lets dual mode devices "pair
  once using either transport method while generating both the BR/EDR and LE
  Long Term Keys (LTK) without needing to pair a second time".
- <https://www.bluetooth.com/learn-about-bluetooth/key-attributes/bluetooth-security/blurtooth/>
  is the SIG description of the same mechanism and its later restrictions.

CTKD is defined for devices that have both radios. A BLE only controller has no
BR/EDR link and no BR/EDR link key to derive from or present, so the camera's
Classic bonding step cannot be satisfied at all. The ESP32-S3 product page
<https://www.espressif.com/en/products/socs/esp32-s3> lists "Bluetooth 5 (LE)"
only. Espressif also declined to implement CTKD:
<https://github.com/espressif/esp-idf/issues/5549> is closed as "Won't Do" after
"ESP32 does not support this feature yet."

Practical conclusion for this fork: the M5StickS3 can never complete a first
time Nikon smart pairing. Not with NimBLE, not with Bluedroid, not with any
firmware change. That is a hardware fact.

### The SnapBridge device identifier is recoverable, but that is a different problem

- <https://github.com/HowenXu/snapbridge-id-extractor> shows how SnapBridge
  generates its 8 byte device ID: `byte[] id = new byte[8]; new Random(new
  Date().getTime()).nextBytes(id)`. It is "generated only once (on first
  run/first pairing) and permanently saved", and "The camera exposes the first 4
  bytes in BLE manufacturer data under Nikon's company ID (0x0399)". Java's
  `Random` is a 48 bit linear congruential generator, so the install timestamp
  seed is brute forceable from those 4 exposed bytes, which recovers the other 4.

This answers gkoh's question in the thread, but not in the way he wanted. It
recovers an existing SnapBridge identity by impersonation. It does not let a new
device register itself with the camera, because registration is what the Classic
bond does. furble does not need to derive anything: it already generates its own
identifier at `lib/furble/Nikon.cpp:33-37`. The camera just has to be told about
it, over Classic.

### Command opcodes, corroborated

The AF, shutter and remote enable opcodes in the issue thread are consistent
with the nsg protocol document and with the reporter's own logs. Remote enable
is `05 00 11 00 <01|00>`, focus is `06 00 12 00 02 <01|00>`, shutter is
`06 00 12 00 03 <01|00>`, and every command is acked with `04 00 12 04`. Focus
and shutter are inert until remote enable has been sent.

For contrast, ML-L7 remote mode writes a single two byte value and has no focus
command at all. gkoh in gkoh/furble#206: "The ML-L7 does not have a focus button
and I could not any way to do focus with the remote UUID." That is why
`NikonRemote::focusPress()` at `lib/furble/NikonRemote.cpp:98` is empty, and it
is correct.

### The geo layout in this tree is right

<https://raw.githubusercontent.com/hurui200320/nsg/master/doc/nikon-z-gps.md>
documents the same 41 byte layout at characteristic `0x2007` that
`nikon_geo_t` uses, including `altitude_ref` as `'P'` or `'M'` at offset 13 and
the sub minute encoding decoded as
`degrees + minutes/60 + submin1/6000 + submin2/600000`. It warns that "The
camera rejects the payload if `altitude_ref` is not set correctly" and that
"When getting ATT status 0x80, it means somehow the camera is rejecting the
GPS."

That is exactly herrfrei's `rc: 384`, and exactly what gkoh/furble#269 fixed.
Two independent sources agreeing is as good as this gets without a camera.

The same document notes that the time characteristic `0x2006` is "not observed
to be required for GPS-only operation" and that "The camera won't update its
time using GPS payload." Combined with herrfrei's observation that geo writes
only succeed when camera time and message time are close, the implication is
that the camera validates the timestamp inside the geo payload against its own
clock rather than adopting it. A sidecar therefore needs an accurate clock, GPS
time being the obvious source, and writing `0x2006` is optional.

### Prior discussion in the upstream tracker

- gkoh/furble#206 is where the Classic transition was first identified: "in this
  mode, the B600 changes from BLE to Bluetooth Classic halfway through handshake
  to do the bonding". It also describes the ML-L7 method, cloning the camera's
  GATT server to make a fake camera and pairing a real ML-L7 against it.
- gkoh/furble#209 is the Z6III bring up. The initial failure there was BLE
  security negotiation, not the handshake: "It claims it succeeded in securing
  the connection, then disconnects. We did not even get a chance to start the
  handshake protocol." It was fixed by disabling BLE security, which is why
  `Device::init()` in this tree no longer calls `setSecurityAuth()` or
  `setSecurityIOCap()`. Worth knowing before anyone reintroduces them.
- <https://blog.furble.net/posts/nikon-ble-reverse-eng/> is gkoh's writeup of
  the SnapBridge APK decompilation and the Ghidra work that identified the
  cipher: "This confirms the handshake is based on the Blowfish cipher." Fetch
  it with curl and a user agent, it rejects some clients with 403.

Note gkoh/furble#211 does not exist. The issue numbers to read are 206, 209 and
257.

## Proposed fix design

### Now, in this PR

Make the smart device failure honest and fast.

`lib/furble/NikonSmart.cpp`, `connectFinalise()`:

1. Log the Bluetooth Classic limitation first, so it is always visible.
2. Keep the final OK wait, but shorten it to a named constant and treat a
   timeout as expected rather than as an error. The function returns `false`
   either way, so the outcome does not change. The 10 s stall does.
3. Leave the identify write and the `false` return alone.

No new setting. There is no behavior to configure: the path already always
fails, this only changes how long it takes and what it says.

### Later, if Nikon smart is ever pursued

Three options, in order of increasing cost.

Option A, import a captured identifier. Add a console command under plan 27 that
sets the 8 byte identifier of a saved Nikon, then complete the smart path:
discover the command and status characteristics by UUID rather than by the raw
handles the reporter hardcoded, add the remote enable write
`05 00 11 00 <01|00>`, and add AF and shutter as `06 00 12 00 <02|03> <01|00>`.
Geodata already works once the path is reachable. This makes furble usable for
anyone who has ever paired the camera with SnapBridge. It does not remove the
SnapBridge dependency, which is the stated reason the project exists, so gkoh is
unlikely to take it upstream. It could live behind a fork setting defaulting
off.

Option B, pair on a Classic capable board. A Bluedroid build for the classic
ESP32 boards only, doing the full BLE plus Classic pairing, writing the
identifier into the normal `nikon_t` record. S3, C3 and C6 boards would then
reconnect to a camera paired elsewhere. This matches gkoh's own comment about a
Nikon specific build. There is now a working reference for it in the nsg ESP32
firmware linked below. It is still a large piece of work and it needs the
`btm_sec.c` patch the reporter found, which means carrying an ESP-IDF patch.

Option C, full Bluedroid migration. gkoh already tried and reported that
Fujifilm, Sony and Nikon smart cannot coexist in one Bluedroid build because of
LE privacy handling. Treat as closed unless that changes.

Recommendation for this fork: do not implement any of them. Ship the diagnostic
fix, keep this document as the record, and revisit only if gkoh lands a Classic
capable Nikon build upstream.

## Verification plan

Local hardware here is an M5StickS3 with Fujifilm cameras and the FauxNY
software camera. There is no Nikon body available, so nothing in the Nikon path
can be exercised locally.

What is verified locally:

- `FURBLE_VERSION=dev FURBLE_TEST=0 pio run -e m5stick-s3` builds clean.
- clang-format clean.
- Fujifilm connect, shutter and geodata still work on hardware. The change is
  confined to `NikonSmart::connectFinalise()`, so this is a regression check
  only.
- FauxNY connect and shutter still work.

What the issue reporters would need to test, if anyone picks up option A or B:

- h3ifri, Z50II: confirm whether the body exposes characteristic `0x2087` on the
  `de00` service. This settles H4. A plain `nRF Connect` service dump is enough,
  no firmware needed.
- h3ifri: confirm the exact UUIDs behind the handles their patch hardcodes as
  `SMART_STATUS_HANDLE = 0x005f` and `SMART_CMD_HANDLE = 0x0062`. Raw handles
  are not portable across bodies or firmware revisions and must not be shipped.
- h3ifri: confirm whether a full SnapBridge uninstall and camera side "delete
  paired device" makes the captured identifier stop working. They noted they did
  not test this. If it survives, the identifier is stored per camera and option A
  is viable. If it does not, option A only works until the user unpairs.
- herrfrei, Z6III: retest geodata against unmodified fork master plus option A,
  to confirm gkoh/furble PR 269 fixed the `rc: 384` for good, and to confirm the
  camera time versus message time constraint they reported.
- Either: whether the final OK notification on `0x2008` ever arrives on any
  body. If some older body does send it, H3 stays a shortened wait rather than a
  removal, which is what this PR does.

## Risks

- The diagnostic change touches a path that no local hardware can exercise. It
  is confined to logging and a timeout constant, and the return value is
  unchanged on every path.
- Declaring vendors: Nikon is untested. Fujifilm is hardware tested. All other
  vendors are code review only.

## Dependencies

None. Independent of every other plan. Option A above would depend on plan 27
for the console surface.
