# 343 review feedback

A review of PR 480, the Apple companion UI snapshot. Two findings were left open
on the first head, `6eb2fd08`: the baseline was unproven on the CI runner image
and the `List` row flattening was unproven. Both were real gaps in what the pull
request could show, and both are now closed by a test or by measured output
rather than by argument. The numbers below come from the Apple workflow on the
pushed head; the run is named in each row.

| # | Severity | Source | Finding | Resolution | Evidence |
| --- | --- | --- | --- | --- | --- |
| B2 | Blocking | PR review | The snapshot baseline is unproven on the `macos-15` runner image. It was authored on a developer host (macOS 27.2.1, Swift 6.4.2), and cross-image font rasterisation equality was asserted rather than shown. A job that renders and writes its own baseline would prove nothing. | Fixed, and shown to be already compared. The baseline is committed, `FURBLE_APPLE_SNAPSHOT_UPDATE` is refused when `CI` is set, and the comparison now prints the baseline path, the host version and the measured deltas, so a green job carries the comparison rather than only a passing suite. `plans/implemented/343-apple-ui-snapshot.md` gained a `Baseline provenance` table naming the authoring host and the comparing image. | `swift-package` on `macos-15-arm64` image `20261118.0550.1`, macOS 15.8.2 (24H232), Xcode 16.4: `Test statusViewMatchesCommittedBaseline() passed`, `Test run with 104 tests passed`, with no baseline written and none missing. The `apple-project` macOS `xcodebuild test` lane compared the same baseline with `Test run with 45 tests passed` and `** TEST SUCCEEDED **`. The same job printed `snapshot comparison: .../Tests/Snapshots/CompanionStatusView.1x.png matched a fresh render on Version 15.8.2 (Build 24H232): 360x168, 60480 pixels, 49 beyond 8/255 (0.08%, budget 1.00%), largest channel delta 46`, so the committed baseline is compared, the comparison is reported, and the cross-image difference is measured rather than assumed. |
| B3 | Blocking | PR review | The `List` row flattening is unproven and needs an `xcodebuild` lane. The snapshot renders `CompanionStatusView` outside a `List`, so a body of four views and a `VStack` look the same in a render, while the app depends on SwiftUI flattening the body into one row per value. | Fixed. `Tests/FurbleCompanionCoreTests/CompanionStatusListRowTests.swift` hosts the shipped section in the app's own shape, `List { Section("Status") { CompanionStatusView(status:) } }`, and counts the rows SwiftUI builds. Controls: a one-view section (section chrome) and the same body wrapped in a `VStack` (the shape that would collapse). The test runs in the existing `swift test` target and in the `apple-project` macOS `xcodebuild test` lane. | Measured on macOS 27.2.1: 5 rows for the flattened section, 2 for the one-view control, 2 for the `VStack` control, with and without a window and at a 30 point list height. The assertion is `flattened == oneView + 4` and `collapsed == oneView`, so the test also fails if it stops distinguishing the two shapes. A hosted `List` with no `NSTableView` fails with the view classes it walked instead of skipping. The `swift-package` job on `macos-15-arm64` printed `list row comparison: Status section 5 rows, one-view control 2 rows, VStack-wrapped control 2 rows, on Version 15.8.2 (Build 24H232)` and `Test statusSectionBuildsOneRowPerValue() passed`, so the counts hold on the runner image as well, in the same job that compares the snapshot. |

Neither finding required a design decision: no new CI job, no new test bundle and
no baseline change. The two tests split the same way the review does, with the
snapshot owning row content, order and spelling, and the row count owning how
many rows the section produces.
