# 62: Configurable button behavior (upstream issue 140)
Status: implemented in this worktree.

## Motivation

Upstream issue [gkoh/furble#140](https://github.com/gkoh/furble/issues/140)
asks for a settings option that changes how the buttons work. The requester
wants the main button to do both focus and shutter: single click focuses,
double click or long press releases the shutter. The separate focus button
(B button) is hard to reach one handed on a stick form factor.

gkoh responded positively but named two blockers at the time:

1. The shutter loop was tightly bound to input handling. Changing it to
   support multiple modes would be messy.
2. Double click detection did not exist in LVGL. He tried a homegrown
   version for v3.0.0 and dropped it. He decided to wait for LVGL to ship
   double and triple click event detection.

Both blockers are gone on current fork master:

1. The LVGL UI rewrite (upstream issue 80, closed) landed. Input is fully
   event driven. Physical buttons are LVGL input devices. On the control
   screen they are `LV_INDEV_TYPE_BUTTON` devices mapped to on-screen
   widgets. Shutter and focus are plain LVGL `PRESSED` and `RELEASED`
   events in `UI::handleShutter` and `UI::handleFocus` (src/FurbleUI.cpp).
   The handlers post `Control::CMD_*` onto a FreeRTOS queue. No loop binds
   shutter to input.
2. The fork builds against LVGL 9.4.0 (src/idf_component.yml). LVGL 9.3
   added multi click detection: `lv_indev_get_short_click_streak()` returns
   the click streak counter, updated before each `LV_EVENT_SHORT_CLICKED`.
   No homegrown double click code is needed.

## Verdict

Feasible now. Small, self contained, and a good upstream candidate because
it closes an open enhancement issue with a mechanism gkoh already said he
was waiting for.

## Scope

- New setting `BUTTON_MODE` in `Settings::type_t` with two values:
  - `two-button` (default): current behavior, unchanged.
  - `one-button`: the OK button does everything, per gkoh's own sketch in
    the issue:
    - single click + hold: focus press, held until release.
    - double click + hold: shutter press, held until release.
- Out of scope: arbitrary button remapping, per-button action tables,
  triple click actions. Keep the settings surface small. gkoh prefers fewer
  UI elements.

## Design sketch

- Settings: add `BUTTON_MODE` key (string enum, NVS backed) plus a menu
  entry under Settings. Default keeps current behavior, per plans/README.md
  policy.
- Control screen (`UI::prepareShutterControl` and `configShutterControl`):
  - In one-button mode, register a combined handler on `m_OK` that uses
    `LV_EVENT_SHORT_CLICKED` plus `lv_indev_get_short_click_streak()` to
    classify single versus double click, and `LV_EVENT_PRESSED` /
    `LV_EVENT_RELEASED` / `LV_EVENT_LONG_PRESSED` for the hold phase.
  - Streak timing uses the LVGL indev `long_press_time` and click window.
    Expose no extra tuning setting initially. If the fixed window proves
    finicky (gkoh's stated worry), a follow-up can add a click speed
    setting.
  - The right button keeps focus in one-button mode too. The modes only
    add, never remove, so users with a working two-button habit lose
    nothing.
- Interactions to handle explicitly:
  - Shutter lock: long press on the lock icon already exists and stays.
    The focus-held-then-shutter lock combo only makes sense in two-button
    mode. In one-button mode the lock icon is the only lock path.
  - The known LVGL double `LONG_PRESSED` quirk (see the workaround comment
    in `UI::handleShutterLock`) applies to any new long press logic. Reuse
    the same require-release guard.
  - Vendor caveats: focus press is a no-op for CanonEOSSmart and
    NikonRemote, and Ricoh repurposes focus as a 2 s self timer
    (lib/furble). One-button mode must not assume focus feedback exists.
    The command queue path is identical, so no vendor code changes.
- No changes to `Control` command handling. The console and companion setting
  metadata expose `BUTTON_MODE`, while their existing command producers keep
  sending the same four commands.

## Dependencies on existing plans

- 27-usb-console: the console `shutter` and `focus` commands exercise the
  command queue directly and stay mode independent. Useful as the control
  during testing but not a dependency.
- 25-multiconnect-ui: touches the Connected page grid, not the control
  screen handlers. No conflict expected, but coordinate if both land in the
  same window.
- 17-imu-gestures (double tap shutter): a future consumer of the same
  "gesture to command" classification. Keep the click classification logic
  in one small helper so 17 can reuse the pattern.
- No power plan dependencies. The handlers run inside the existing LVGL
  task.

## Implementation state

Implemented in the requested isolated worktree. Notes:

- `BUTTON_MODE` is an NVS-backed string enum. Its key is `button_mode` and its
  default is `two-button`. Its companion wire id was renumbered from the
  provisional 46 to 27 during the rebase onto current fork master. 27 is the
  lowest free positive id in the settings ledger: master assigns 0-26 and
  28-35 (33 took 30, 118 landed no new id), leaving 27 as the single gap. The
  NVS key string stays `button_mode` because it is a name, not the wire id.
- Rebased onto current fork master, which now includes #33 (exposure preset
  picker, wire id 30) and #118 (sim per-model physical buttons). The enum and
  storage_type conflicts kept both PRESET_PICKER and BUTTON_MODE. The golden
  protocol corpus was regenerated with `make -C tests/protocol generate`; it
  now carries `settings/*-27.bin` fixtures for BUTTON_MODE and the host
  protocol test passes.
- The setting is available at Settings > Features. The default two-button
  callback delegates to the existing shutter handler, so the default input
  path is unchanged.
- One-button mode uses the LVGL click streak and a guarded combined handler
  for the main button. The right button remains a focus control. The lock
  icon remains the one-button lock path. The three gestures are: single
  press-and-hold dispatches focus (focus press on the hold, focus release on
  release); a double click dispatches a single shutter press and release; a
  click-then-hold dispatches a single sustained shutter press and release. A
  lone quick tap is a no-op by design.
- Console and companion setting paths accept and report both string values.
  Invalid companion writes are rejected. The initial design said not to
  change those services, but exhaustive setting metadata cases are required
  for this base, so both paths include `BUTTON_MODE`.
- LVGL 9.4 has no public getter for `long_press_time`. The handler uses the
  default 400 ms window for its stale-streak guard, while LVGL supplies the
  click streak through `lv_indev_get_short_click_streak()`.
- Clang-format 21 and `git diff --check` pass on every changed file.
- `FURBLE_VERSION=dev FURBLE_TEST=0 pio run -e m5stick-s3-debug` builds clean
  (RAM 11.5%, Flash 75.9%).
- Sim dispatch scenario `sim/scenarios/e2e/button-mode-dispatch.txt` exercises
  the real `handleButtonMode` state machine through the FauxNY camera: the
  default two-button mode fires the shutter on a main-button press; one-button
  mode dispatches focus on a single press-and-hold, a single shutter press and
  release on a double click, and a single sustained shutter press and release
  on a click-then-hold. The scenario asserts the dispatched commands through
  new `camera.focus_presses` / `camera.focus_releases` sim observers that
  mirror the existing shutter counters. For the double click and the
  click-then-hold it asserts both presence (one shutter pair) and absence
  (`focus_presses` unchanged), which is the check that catches the
  leading-focus leak. Teeth were verified by mutation: reintroducing the eager
  focus on the first press makes the scenario fail on `camera.focus_presses`
  (expected 1, got 2) at the double-click step; the fix passes. All 11 e2e
  scenarios pass.
- Coverage boundary: the SDL sim models discrete button events, not LVGL's
  400 ms short-click streak-timing window. FURBLE_SIM-only seams (a
  `button-mode` setter action, `main-press-hold` / `main-double-click` /
  `main-click-hold` gesture actions that replay the full real event stream,
  and an injected click streak read only in the sim build) let the scenario
  drive the dispatch decision. The firmware binary is unchanged: every seam is
  guarded by `#if defined(FURBLE_SIM)`. The real streak-timing feel stays a
  hardware gap.
- No sdkconfig files changed.

## Hardware bug: leading-focus leak on multi-click (2026-08-21)

On-device testing (M5StickS3 + Fujifilm X100VI, serial capture) confirmed
gesture 1 (single press-and-hold = focus) worked, but gestures 2 and 3 did
not:

- The original one-button handler fired the single-click focus action
  immediately on the first press, then detected the click streak and fired the
  shutter. On a double click the serial log showed `focusPress` / `focusRelease`
  from the first click leaking before the `shutterPress` / `shutterRelease`
  pair. Click-then-hold was unreliable for the same reason, and its shutter
  timing collapsed.
- Root cause: focus cannot be decided at press time, because a first press may
  turn out to be the first half of a multi-click gesture.
- Fix (src/FurbleUI.cpp `handleButtonMode`): defer the single-click focus.
  Focus now engages only on `LV_EVENT_LONG_PRESSED` of a first press. A press
  that follows a recent short click (inside the 400 ms streak window) drives
  the shutter directly: `CMD_SHUTTER_PRESS` on that press, `CMD_SHUTTER_RELEASE`
  on its release. This unifies double click (quick release = tap) and
  click-then-hold (held release = sustained) with no leading focus. A lone
  quick tap is a no-op. Two-button mode is untouched. The unused
  `m_ButtonModeDoubleClick` member was removed.
- The sim scenario was tightened so it would have caught this: the multi-click
  actions now replay the first click's real press and release, and the scenario
  asserts `focus_presses` does not increment on the double click or the
  click-then-hold. Mutation-verified (fail before, pass after).
- Merge held: on-device gesture retest is required before merge. Confirm on
  hardware that a double click fires one clean photo with no focus leak, and
  that a click-then-hold holds the shutter for the hold duration. The 400 ms
  double-click window and click-then-hold feel still need the physical
  M5StickS3. No camera hardware was exercised for this fix.
