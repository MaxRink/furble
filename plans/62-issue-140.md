# 62: Configurable button behavior (upstream issue 140)

Status: research, no implementation yet.

## Motivation

Upstream issue [gkoh/furble#140](https://github.com/gkoh/furble/issues/140)
asks for a settings option that changes how the buttons work. The requester
wants the main button to do both focus and shutter: single click focuses,
double click or long press releases the shutter. The separate focus button
(B button) is hard to reach one handed on a stick form factor.

gkoh responded positively but named two blockers at the time:

1. The shutter loop was tightly bound to input handling. Changing it to
   support multiple modes would be messy.
2. Double click detection did not exist in LVGL. He tried a homegrown
   version for v3.0.0 and dropped it. He decided to wait for LVGL to ship
   double and triple click event detection.

Both blockers are gone on current fork master:

1. The LVGL UI rewrite (upstream issue 80, closed) landed. Input is fully
   event driven. Physical buttons are LVGL input devices. On the control
   screen they are `LV_INDEV_TYPE_BUTTON` devices mapped to on-screen
   widgets. Shutter and focus are plain LVGL `PRESSED` and `RELEASED`
   events in `UI::handleShutter` and `UI::handleFocus` (src/FurbleUI.cpp).
   The handlers post `Control::CMD_*` onto a FreeRTOS queue. No loop binds
   shutter to input.
2. The fork builds against LVGL 9.4.0 (src/idf_component.yml). LVGL 9.3
   added multi click detection: `lv_indev_get_short_click_streak()` returns
   the click streak counter, updated before each `LV_EVENT_SHORT_CLICKED`.
   No homegrown double click code is needed.

## Verdict

Feasible now. Small, self contained, and a good upstream candidate because
it closes an open enhancement issue with a mechanism gkoh already said he
was waiting for.

## Scope

- New setting `BUTTON_MODE` in `Settings::type_t` with two values:
  - `two-button` (default): current behavior, unchanged.
  - `one-button`: the OK button does everything, per gkoh's own sketch in
    the issue:
    - single click + hold: focus press, held until release.
    - double click + hold: shutter press, held until release.
- Out of scope: arbitrary button remapping, per-button action tables,
  triple click actions. Keep the settings surface small. gkoh prefers fewer
  UI elements.

## Design sketch

- Settings: add `BUTTON_MODE` key (string enum, NVS backed) plus a menu
  entry under Settings. Default keeps current behavior, per plans/README.md
  policy.
- Control screen (`UI::prepareShutterControl` and `configShutterControl`):
  - In one-button mode, register a combined handler on `m_OK` that uses
    `LV_EVENT_SHORT_CLICKED` plus `lv_indev_get_short_click_streak()` to
    classify single versus double click, and `LV_EVENT_PRESSED` /
    `LV_EVENT_RELEASED` / `LV_EVENT_LONG_PRESSED` for the hold phase.
  - Streak timing uses the LVGL indev `long_press_time` and click window.
    Expose no extra tuning setting initially. If the fixed window proves
    finicky (gkoh's stated worry), a follow-up can add a click speed
    setting.
  - The right button keeps focus in one-button mode too. The modes only
    add, never remove, so users with a working two-button habit lose
    nothing.
- Interactions to handle explicitly:
  - Shutter lock: long press on the lock icon already exists and stays.
    The focus-held-then-shutter lock combo only makes sense in two-button
    mode. In one-button mode the lock icon is the only lock path.
  - The known LVGL double `LONG_PRESSED` quirk (see the workaround comment
    in `UI::handleShutterLock`) applies to any new long press logic. Reuse
    the same require-release guard.
  - Vendor caveats: focus press is a no-op for CanonEOSSmart and
    NikonRemote, and Ricoh repurposes focus as a 2 s self timer
    (lib/furble). One-button mode must not assume focus feedback exists.
    The command queue path is identical, so no vendor code changes.
- No changes to `Control`, the console, or the companion service. All three
  producers keep sending the same four commands.

## Dependencies on existing plans

- 27-usb-console: the console `shutter` and `focus` commands exercise the
  command queue directly and stay mode independent. Useful as the control
  during testing but not a dependency.
- 25-multiconnect-ui: touches the Connected page grid, not the control
  screen handlers. No conflict expected, but coordinate if both land in
  the same window.
- 17-imu-gestures (double tap shutter): a future consumer of the same
  "gesture to command" classification. Keep the click classification logic
  in one small helper so 17 can reuse the pattern.
- No power plan dependencies. The handlers run inside the existing LVGL
  task.

## Verification plan

- FauxNY camera: enable one-button mode, confirm the log sequence
  focus press, focus release, shutter press, shutter release matches the
  gesture performed. Cover: single click, single click + hold, double
  click, double click + hold, and the lock icon path.
- Regression: default mode unchanged; repeat the current manual button
  matrix (shutter press/release, focus press/release, lock combo).
- Hardware: M5StickS3 with a Fujifilm body before any PR, per repo policy.
  Verify half press autofocus on single click + hold and burst on double
  click + hold.
- Console cross-check: `status` and `shutter`/`focus` console commands
  confirm the queue still behaves identically in both modes.
- Timing sanity: test the double click window at default LVGL settings
  with two people. If it feels finicky, revisit before proposing upstream.

## Upstream path

Issue first, per process. Comment on issue 140 that LVGL 9.3+ ships
`lv_indev_get_short_click_streak()` and propose the two-mode setting.
Implement only after gkoh agrees on the gesture mapping.
