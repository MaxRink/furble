# XINLUDA XL9555

**Part and package.** XINLUDA XL9555, a 16-bit I2C IO expander, pin and
register compatible with the TI PCA9555 family. Package options and the pad
count were not read and are UNVERIFIED.

**Status.** future. `lib/hal/XL9555.cpp` is a pure driver and no shipped board
instantiates it: the only caller in the tree is `tests/host/hal_drivers_test.cpp`,
and `plans/implemented/322-hardware-abstraction.md` is the first board that will use it, for
the T-LoRa Pager GPS enable line and the T-Watch Ultra rails.

**Role in furble.** GPIO the SoC does not have. The planned boards use it for the
Pager GPS enable and the Watch Ultra rails (`plans/implemented/322-hardware-abstraction.md`,
phase 1 audit, XL9555 row; `plans/318-next-board-battery-gps.md`). Every call is
a read-modify-write of the live register, so the driver holds no cache that an
expander reset could invalidate (`lib/hal/XL9555.h:18`).

**Documents.** [XL9555-DS]

### The register-pair walk, and the address strap

The XL9555 is an input-compatible clone of the NXP PCA9555, and that document
states the pair rule in words the XL9555's own table only shows: "if the first
byte is sent to Output Port 1 (register 3), the next byte is stored in Output
Port 0 (register 2)", and on the read side "if Input Port 1 is read, the next
byte read is Input Port 0" (PCA9555, Rev. 1, 25 April 2023, sections 6.1 and the
read sequence figures). The host fake models exactly that, and the driver never
performs a multi-byte transfer, so the model exists to stop a future change from
walking out of a pair.

The strap is the part the driver cannot express. `ADDRESS_BASE` is 0x20 and no
code reads it, because `RegisterBus` is already bound to one address. A board
that carries two expanders, or one with A2 to A0 strapped away from 0b000, has to
bind the shifted address in its own bus adapter. That is a coverage gap, in the
list below.

## Where the code implements it

- `lib/hal/XL9555.cpp:24` `setInput()`: sets the configuration bit, which also
  selects the weak pull-up.
- `lib/hal/XL9555.cpp:28` `setOutput()`: writes the level first, then clears the
  configuration bit, so an active-high enable such as a GNSS rail never sees the
  stale power-on level.
- `lib/hal/XL9555.cpp:32` `write()` and `:36` `read()`: level change and read
  back through the live registers.
- `tests/host/hal_drivers_test.cpp`: pins the command bytes, the port split and
  the write-before-direction order.
