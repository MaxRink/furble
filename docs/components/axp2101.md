# X-Powers AXP2101

**Part and package.** X-Powers AXP2101, a single-cell NVDC PMU with an E-gauge
fuel gauge, QFN5*5 with 40 pins. Section 8.1 Package gives the outline and the
marking table ([AXP2101-DS10], section 8.1, page 59). Pad pitch and exposed pad
size were not read and are UNVERIFIED.

**Status.** future. `lib/hal/AXP2101.cpp` is a pure driver and no shipped board
instantiates it: the only caller in the tree is `tests/host/hal_drivers_test.cpp`,
and `plans/implemented/322-hardware-abstraction.md` is the first board that will use it. M5
boards that carry an AXP2101 keep the pinned library's own path.

**Role in furble.** The register driver for boards the pinned board support
library does not know. M5 boards keep the library's own AXP2101 path. The
driver covers the subset of rails, ADC readings, the fuel gauge, the backup
cell charger and the power key that a non-M5 board needs
(`plans/implemented/322-hardware-abstraction.md`, phase 1 audit).

**Documents.** [AXP2101-DS10], [AXP2101-DS14], [AXP2101-DS01]

Row 12 cites both places because they say different things. Section 6.12.2 is
headed BACKUP and gives the enable bit and voltage range in prose. The bit
encoding of the voltage register itself is only in 6.13.2.67. The driver had
named 6.12.2 alone for the enable and 6.13.2.67 for the voltage, which split one
pair of facts across two citations for no reason.

Row 17 does not describe the driver. The driver expects 0x4A at register 0x03.
Revision 0.1 documents 0x47 or 0x57 for the two silicon revisions and neither
2021 nor 2022 revision carries the register. So the driver constant is
unconfirmed against a datasheet and the mismatch is open. It is recorded here
rather than changed, because a driver edit needs a device to test on.

The third verification pass (plan 385) found a second vendor source for the
value without closing the row. The pinned M5Unified 0.2.20 drives the same part
on Core2 v1.1 boards, and `AXP2101_Class.cpp` lines 31 to 34 read register 0x03
and reject anything but 0x4A, exactly as `AXP2101::probe()` does. Two independent
vendor implementations therefore agree that the shipping silicon answers 0x4A
where revision 0.1 printed 0x47 or 0x57. That raises the row from "unconfirmed"
to CORROBORATED and leaves it open: no X-Powers revision states it, and a
register read on a board with the part is still what would settle it.

### REG 90 bit 4, settled three ways

The driver reads REG 90 bit 4 as BLDO1. The three revisions agree the field is
BLDO1 and one of them prints the wrong description:

| Copy | What REG 90 bit 4 says | Where |
| :--- | :--- | :--- |
| revision 1.0 | "aldo1 enable", a second copy of bit 0 in the same table | section 6.13.2.75, page 53 |
| revision 1.4 | "bldo1 enable" | section 6.13.2.75, page 53 |
| revision 0.1 | the field name in the 0x90 table is `bldo1_en`, and the description beside it still reads "aldo1 enable" | register 0x90 field table, page 44 |

The revision history explains the split. Revision 1.4 page 2 records revision
1.2, April 21, 2022, as "1. Update package in Chapter8.1, 2. Revise reg 90 in
Chapter6.13". So the "aldo1 enable" text is a revision 1.0 defect that was fixed
two revisions later, and revision 0.1's field name shows what the field always
meant. The comment at `lib/hal/AXP2101.cpp:47` to `:49` is right, it is load
bearing, and `REG_LDO_EN0` is now VERIFIED.

The verification pass also reported a copy labelled SWcharge V1.0 reading
"bldo1 enable". This corpus did not open that copy, so it is not cited.

## Facts still unverified

- The `CHIP_ID` value 0x4A and whether register 0x03 answers on real silicon at
  all. Revision 0.1 documents 0x47 or 0x57, and the two later revisions drop the
  register, which is consistent with a pre-production feature that did not ship.
- Package pad pitch and exposed pad size.
- Whether the stale-value behaviour the driver describes for a disabled gauge is
  specified anywhere. Section 6.13.2.88 says only that A4 is read only and holds
  the percentage.
- Which of the two revision 0.1 identity values, 0x47 or 0x57, shipped on the
  M5 Core2 v1.1 boards that carry this part.
- Any errata. None was found.
