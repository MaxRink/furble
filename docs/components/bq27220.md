# Texas Instruments BQ27220

**Part and package.** TI BQ27220, a single-cell CEDV fuel gauge with an I2C
interface. The driver does not depend on the package; the datasheet front
matter names a 9-ball WCSP and a 12-pin WSON variant, and the exact package of
a given board is UNVERIFIED for this page.

**Status.** future. `lib/hal/BQ27220.cpp` is a pure read-only driver and no
shipped board instantiates it: the only caller in the tree is
`tests/host/hal_drivers_test.cpp`, and `plans/implemented/322-hardware-abstraction.md:112-113`
names the T-LoRa Pager as the first board that will use it.

**Role in furble.** Reads voltage, current, state of charge, time to empty and
the battery status word so a board with a gauge reports real battery figures.
Read-only: the driver never unseals the gauge and never touches data memory
(`lib/hal/BQ27220.h:6` to `:16`).

**Documents.** [BQ27220-TRM]

### Two errors in the manual

Both were read in the revision above and both are the vendor's, not the
driver's.

| Where | What it prints | What the manual's own body says |
| :--- | :--- | :--- |
| Table 2-1 Standard Commands, page 17 | `Current()` with the unit `mAh` | Section 2.8, page 23: "Units are mA." |
| Table 2-1 Standard Commands, page 17 | the name `RelativeStateOfCharge()` at 0x2C and 0x2D | Section 2.21, page 23, is headed `StateOfCharge(): 0x2C and 0x2D` |

Neither affects the driver, which reads the command codes and takes the units
from the section bodies. They are recorded so a future reader who greps Table 2-1
for mAh does not conclude that Current() is an accumulated charge.

## Where the code implements it

- `lib/hal/BQ27220.cpp:32` `word()`: reads two bytes at the command code and
  assembles them low byte first.
- `lib/hal/BQ27220.cpp:41` `read()`: five commands, any failure fails the whole
  reading, percent capped at 100, status bits split into `present` and
  `discharging`.
- `tests/host/hal_drivers_test.cpp`: expected command bytes and status bits are
  stated from the manual, not from the driver constants.

## Hardware constraints

The command pacing in the technical reference manual is a bus timing
constraint, not a register. `read()` asks the bus for the gap before every
packet after the first.

| Constraint | Document and section | Where it bites | State |
| :--- | :--- | :--- | :--- |
| At least 66 us of t(BUF) bus-free time between all packets addressed to the gauge, use individual 1-byte writes above 100 kHz, and do not issue all standard commands more than twice per second or the watchdog timer can reset the gauge | BQ27220-TRM section 5.3 I2C Command Waiting Time, pages 63 and 64 | `lib/hal/BQ27220.cpp:44` to `:49`, `lib/hal/BQ27220.h:35` | VERIFIED |
| `read()` issues its five standard commands in one call, Voltage 0x08, BatteryStatus 0x0A, Current 0x0C, TimeToEmpty 0x16 and StateOfCharge 0x2C, and asks the bus for the 66 us gap before every packet after the first | Same pacing limit, read against the driver; the pacing loop was added in #479 | `lib/hal/BQ27220.cpp:27` to `:29`, `:41` to `:53` | VERIFIED |
| The delay hook's default does nothing, so an adapter that drives the gauge without overriding it leaves the 66 us gap unimplemented | Read against the driver; `lib/hal/BQ27220.h:17` to `:21` records the requirement | `lib/hal/HalBus.h:52`, seam note at `:24` to `:29` | VERIFIED |

Section 5.3 is the whole constraint in two sentences. "To ensure proper
operation at 400 kHz, a t(BUF) >= 66 us, bus-free waiting time must be inserted
between all packets addressed to the fuel gauge. In addition, if the SCL clock
frequency is > 100 kHz, use individual 1-byte write commands for proper data flow
control." Page 64 adds that for read-only standard commands "the host should not
issue all standard commands more than two times per second. Otherwise, the fuel
gauge could result in a reset issue due to the expiration of the watchdog timer."

The driver is unconnected. No file under `src/`, `include/` or `components/`
includes `BQ27220.h` at this commit, so the five-command burst cannot happen on
a board today. The pacing is implemented, and the latent risk is the adapter:
the hook's default is a no-op, so the first board that wires the driver must
override `delayUs` or the gauge watchdog may reset the part mid-read.
