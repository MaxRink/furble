# Bosch BMI270

**Part and package.** Bosch Sensortec BMI270, a six-axis inertial measurement unit
with an integrated feature engine. Package and pinout were not read and are
UNVERIFIED.

**Status.** shipped. `m5stick-s3` is the only board that carries the part, and
`src/FurbleIMUMotionBMI270.cpp` drives it for motion wake.

**Role in furble.** The IMU and any-motion source on the StickS3. furble uses the
feature engine for any-motion and no-motion instead of polling, so the IMU stays
in a low power state between events (`src/FurbleIMUMotionBMI270.cpp:17` to `:80`).

**Build scope.** M5Unified carries its own BMI270 driver together with an
8,192-byte initialisation blob, and its IMU probe references the blob, so
`--gc-sections` cannot drop it. Both are compiled only where a lane passes
`FURBLE_IMU_BMI270=1`, which is the default, so a board that carries the part
cannot lose it by omission. The Core family passes `-DFURBLE_IMU_BMI270=0`,
because its IMU is an MPU6886 or MPU9250 and an image pinned to `board_M5Stack`
can never run that probe (plans/347).

**Documents.** [BMI270-DS], [BMI270-API]

Row 8 replaces a claim this page used to make. It said the any-motion and
no-motion feature layout was described only by the SensorAPI and not by the
datasheet. That was false. Section 5.2.40 devotes pages 88 to 93 to the FEATURES
register block, and the any-motion page inside it, page 92, prints both registers
with their bit fields, ranges and defaults. The SensorAPI is a convenience, not
the only source, and the corpus no longer says otherwise.

The threshold scale is arithmetic on two datasheet values. The datasheet gives
the range as 0 to 1 g over 11 bits and the default as 0xAA = 83 mg. 0xAA is 170
counts, so 83 mg over 170 counts is 0.488 mg per count. The datasheet does not
print a mg per LSB figure, so this is a derivation and the page labels it as one
rather than as a quoted specification.

## Tuning values and units

One duration count is one 50 Hz sample, which is 20 ms, and the slope threshold
field spans 0 to 1 g over 11 bits, so one count is about 0.488 mg. Both are
datasheet facts; the resolution is the range divided by the field width and the
page states the arithmetic rather than a per-count table
(`BMI270-DS` section 5.2.40, page 92).

| Value | Setting | Effective | Citation |
| :--- | ---: | :--- | :--- |
| `ANY_MOTION_DURATION` | 1 | 20 ms, the shortest the chip offers, because leaving stationary has to be immediate | `src/FurbleIMUMotionBMI270.cpp:102` |
| `ANY_MOTION_THRESHOLD` | 0xAA | about 83 mg, the Bosch default, and 170 counts at 0.488 mg | `src/FurbleIMUMotionBMI270.cpp:103` |
| `NO_MOTION_DURATION` | 3000 | 60 s, matching the software backend exactly | `src/FurbleIMUMotionBMI270.cpp:107` |
| `NO_MOTION_THRESHOLD` | 0x090 | about 70 mg, the Bosch default | `src/FurbleIMUMotionBMI270.cpp:108` |
| `POLL_INTERVAL_MS` | 1000 | status poll cadence | `src/FurbleIMUMotionBMI270.cpp:77` |

The 60 s stationary hold is the shared motion contract across all three backends
(`src/FurbleIMU.cpp:24-29`). The driver's own comment uses 0.48 mg per count, so
the wake threshold is consistent with the datasheet field and is not four times
too insensitive.

### The output-configuration field, still open

The threshold word of both engines carries the slope threshold in bits 10:0, the
output configuration in bits 14:11 and the enable in bit 15 (section 5.2.40,
pages 92 and 93). The driver preserves bits 14:11 from whatever the
configuration file M5Unified uploaded left there, on the stated reading that
Bosch's own code never writes them
(`src/FurbleIMUMotionBMI270.cpp:88-96`, `src/FurbleIMUMotionBMI270.cpp:169-176`).
Plan 385 could not settle whether preserving that value is equivalent to
clearing it: Bosch's `bmi270_anymotion_config()` builds both words from scratch,
which would clear the field. The row is therefore UNVERIFIED, and what settles it
is a scope on INT1 with the two settings, or the SensorAPI source rather than its
headers.

## Error handling and ordering

- Every feature access brackets advanced power save, the way `bmi270.c` does
  around its own feature writes. On the StickS3 the bracket is inert because
  M5Unified writes `PWR_CONF` 0x00 during `begin()` and never turns power save
  back on, and it is kept because a silently dropped feature write is
  indistinguishable on the bench from a dead interrupt
  (`src/FurbleIMUMotionBMI270.cpp:65-69`).
- Disarming clears `INT1_IO_CONTROL` to 0x00 so the pin stops driving and
  reverts to its reset state (`src/FurbleIMUMotionBMI270.cpp:43-44`).
- A bus read or write is retried once, because the IMU shares the internal bus
  with the PMIC, which fails its first transaction after idle sleep
  (`src/FurbleIMUMotionBMI270.cpp:110-133`).
- All IMU bus access is serialized by `g_IMUMutex`, held across a whole
  read-modify-write sequence and never across a delay
  (`include/FurbleIMU.h:31-38`).
