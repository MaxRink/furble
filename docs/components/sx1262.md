# Semtech SX1262

**Part and package.** Semtech SX1262, a sub-GHz LoRa transceiver, +22 dBm
variant. The package is a QFN with an exposed pad; the pad count and size were
not read and are UNVERIFIED.

**Status.** future. `lib/hal/SX1262.cpp` is a pure driver and no shipped board
carries the part: the only caller in the tree is `tests/host/hal_drivers_test.cpp`,
and `plans/implemented/322-hardware-abstraction.md:38` names the T-Beam, the Pager, the Watch
Ultra and the Cardputer Cap as the boards that will need it.

**Role in furble.** furble has no use for the radio, but a board that carries
one must hold it in its lowest state. Left alone it idles in STDBY_RC, and any
falling edge on NSS wakes it. The driver pulses the reset pin, waits for BUSY,
sends SetSleep and confirms the part is asleep
(`lib/hal/SX1262.h:7` to `:30`).

**Documents.** [SX1262-DS]

## Error handling and the NSS rule

`sleep()` returns false when BUSY never drops, when the SPI write fails, or when
BUSY is not high afterwards, and it sends no SetSleep in the first two cases
(`lib/hal/SX1262.h:55-61`, `lib/hal/SX1262.cpp:14-25`).

Any falling edge on NSS wakes the chip, so the board adapter must keep NSS high
through MCU light sleep and deep sleep (`lib/hal/SX1262.h:26-27`). An adapter
that drives NSS low in sleep undoes the whole sequence.

## Known limitations instead of errata

No Semtech errata document exists for the part. Section 15 Known Limitations,
pages 109 and 110, is the substitute and lists four cases: modulation quality at
500 kHz LoRa bandwidth with the workaround through bit 2 of register 0x0889, PA
clamping under antenna mismatch, the implicit header timeout, and inverted IQ.
A board that uses a 500 kHz bandwidth has to apply the workaround itself, because
the driver only sleeps the part.

## Where the code implements it

- `lib/hal/SX1262.cpp:25` `sleep()`: reset pulse, BUSY poll with a 10 ms budget,
  a two-byte SetSleep frame, the 500 us settle, then a BUSY-high poll with a
  5 ms budget, 15,700 us in the worst case.
- `lib/hal/SX1262.h:50` to `:60`: the `Port` seam the board implements, so the
  driver holds no SDK include.
- `tests/host/hal_drivers_test.cpp`: pins the opcode, the sleepConfig byte and
  the wait order.

`POLL_US` at `lib/hal/SX1262.h:78` is a driver choice, not a datasheet figure.
It sets how often the BUSY line is sampled inside the 10 ms budget.

## Hardware constraints

The sleep sequence has two failure modes worth naming, because the driver has
no retry and no caller yet.

- `lib/hal/SX1262.cpp:31` to `:33` returns false when BUSY never drops inside
  the 10 ms budget, before any SetSleep is sent. The radio then stays in
  STDBY_RC, which draws 0.6 mA (Table 3-5, page 17) instead of the 160 nA sleep
  state, so a board that carries the radio must retry the sequence or hold
  NRESET low until it does.
- `lib/hal/SX1262.cpp:46` waits for BUSY high inside the 5 ms budget and
  returns false on a timeout, so a caller can tell "asleep" from "the command
  went out but the chip did not confirm".
- The driver is unconnected: no file under `src/`, `include/` or `components/`
  includes `SX1262.h` at this commit, so no board misses a retry today.

## Facts still unverified

- The opcode table number (Table 13-1) and the sleepConfig encoding table
  (Table 13-2). The driver header cites both; the retrieved text did not include
  them, so the 0x00 encoding and the 0x84 opcode are CITED only.
- The 0.6 mA standby and 160 nA sleep figures, which are CITED from Table 3-5
  without reading the table.
- A reset-to-ready figure. The document has none, so the 10 ms budget rests on
  the reporter's reading of Table 8-2, page 56, which is about SLEEP to STDBY_RC
  and not about reset.
- Externally supplied TCXO behaviour: the driver never configures it, and a
  board whose radio needs a TCXO would have to do that before the sleep call.
- An errata document. None was found, and section 15 Known Limitations is the
  substitute, see above.
- The Table 13-1 opcode table and Table 13-2 sleepConfig encoding. The 0x84 and
  0x00 values are CITED from the driver header.
